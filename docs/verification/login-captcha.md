# 验证码登录：自动优先，人工兜底

> 目标：登录遇到验证码时**先自动过**，过不去再让用户看着图输入；
> 而不是一遇验证码就整条链路失败。

## 为什么这样设计

各平台的登录验证码形态完全不同（图片码 / 短信码 / 滑块）。一刀切的「自动解」
会引出两个真问题：

1. **滑块类没法在无头服务器上解**（极验型），强行做只能引入更复杂的对抗；
2. **错码比不交更糟**：验证码错一次平台就刷新，连续错会把账号打进更严的风控。

所以定成两级：

```
打开登录页 → 填账号密码 → 提交
   │
   ├─ 没弹验证码 / 直接登录成功 ────────────────► done
   ├─ 弹图片验证码
   │    ├─ 自动识别（已配置的多模态模型读图）
   │    │    ├─ 码被接受 → done
   │    │    └─ 码不对 → 刷新图片，最多重试 2 次（AUTO_RETRIES）
   │    └─ 识别不出 / 重试用尽 → manual_captcha（把图交给用户）
   └─ 短信登录 → manual_sms（用户点「获取短信码」、填码提交）
```

## 代码位置

| 文件 | 职责 |
| --- | --- |
| `browser/captcha_ocr.py` | 图片码识别：只输出纯字符；空/不可用/不合形态一律返回空串（**不猜**） |
| `browser/login_session.py` | 登录会话：`LoginSpec`（每平台 DOM）、`InteractiveLogin`（流程）、`LoginSessionManager`（线程 + 浏览器） |
| `api/service.py` | `start_interactive_login` / `login_session_*` / `finish_interactive_login` |
| `api/server.py` | `POST /api/accounts/login/start`、`GET /api/accounts/login/<sid>`、`POST .../code`、`POST .../sms`、`POST .../finish`、`POST .../cancel` |
| 控制台「账号」页 | 按钮「验证码登录」→ 会话面板（截图 + 验证码框 + 短信框 + 保存登录态） |

## 已核实的平台

| 平台 | 状态 | 依据 |
| --- | --- | --- |
| 超星学习通 | ✅ 已写入 `SPECS` | 登录页 `#phone` / `#pwd` / `#loginBtn` 是仓库里已核实的选择器；验证码图片与输入框给的是**候选列表**，运行时按顺序找第一个存在的 |
| 其他平台 | ⛔ 返回 501 `not_supported` | 登录页 DOM 未核实 —— 不猜选择器，宁可明说「暂不支持」 |

## 自动识别用的是什么

复用「工具 → LLM 配置中心」里配的主模型/OCR 模型（`LLMConfig`）：

- 模型没配 → **直接转人工**，不报错；
- 识别结果只接受 3~6 位字母数字，带解释/标点/空格被规范化后仍不合形态就丢弃；
- 每次登录最多自动试 `AUTO_RETRIES=2` 次。

## 验收步骤（需要有账号的人做一次）

1. 控制台「工具」页配好大模型（至少能读图）；
2. 「账号」页 → 验证码登录 → 选超星 → 填账号密码 → 开始登录；
3. 观察状态：
   - 自动识别成功 → 状态直接 `done`，消息里会写「自动识别验证码（xxxx）后登录成功」；
   - 自动失败 → 面板出现验证码图，输入后点「提交验证码」→ `done`；
   - 短信：点「获取短信码」→ 收到后填「短信验证码」→ 提交；
4. 成功后点「保存登录态到账号」，会在 `data/sessions/accounts/<owner>-chaoxing-<id>.cookies.json` 落盘。

## 未验证 / 边界

- 超星的验证码图片选择器与输入框是**候选集合**，真机可能落在别的 class 上；
  失败时状态会停 `manual_captcha` 并带整页截图，按截图补一次选择器即可。
- 滑块类平台（U校园 / iTEST / 品课部分场景）**不在本机制覆盖范围**：无头环境无法拖拽，
  仍走原有的「自动解极验」或「用户本机浏览器登录后抓 Cookie」。
- 会话 TTL 5 分钟，超时自动关浏览器；同一时刻最多 2 个登录会话。
- 本机制只服务**用户本人账号**；不做批量、不绕过任何风控。
